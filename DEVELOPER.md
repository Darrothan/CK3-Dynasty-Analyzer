## Pipeline and provenance

`src/import.ts` extracts and validates plaintext bytes. `src/import.worker.ts` selectively queries Jomini paths and calls `src/model.ts`, then loads Arrow columns into local DuckDB-Wasm through `src/database.ts`. The worker retains the source bytes for the Raw Explorer; it is terminated for cancellation or replacement. No raw save is stored in React state or browser persistence. Source identifiers are strings, not floating-point measures. Each imported save is a separate in-memory session; there is no cross-save identity or merging.

Jomini `typeNarrowing: 'none'` preserves IDs and CK3 date strings. Identical duplicate ID records are collapsed; conflicting character records are omitted with warnings, and other conflicting/invalid records are currently omitted without equivalent detailed reporting. Some missing sections become empty tables. Original entity and link paths are retained where available; use the raw explorer for unsupported fields. Dates in the source are strings, not validated DuckDB dates.

## Localization

The optional directory picker passes selected files to the worker before import. Files ending in `.yml` or `.yaml` are read as strict UTF-8. Entries in the CK3 `key:version \"value\"` format are parsed, including BOM, versionless entries, escaped quotes/backslashes and `$key$` references. Files are sorted by relative path using ordinal comparison; within that order the last definition wins, including later lines in the same file. Conflicting definitions are counted and reported. This deterministic rule is not CK3's complete mod load order.

Embedded direct names are used as supplied unless they match a loaded localization key. Dynasty `localized_name`/`name` is preferred; a dynasty key supplies a name only when localization resolves it. A house uses its `localized_name`, `name`, or a resolvable house key before falling back to its resolved dynasty name. An applicable house prefix takes precedence over a dynasty prefix; resolved localization and clear direct prefixes retain significant whitespace. Raw names, keys, prefixes and source IDs remain available. No name is inferred from an unresolved dynasty ID/key. Direct culture, faith, rite, religion and title names are preferred to their keys. Trait lookup keys prefer `trait_<key>` before the raw key, avoiding unrelated collisions such as `brave`. Dynasty search is case- and accent-insensitive. Simple formatting markers are removed; unresolved references, cycles and dynamic expressions fall back to their original key rather than fabricating a value. Other CK3 scripting/formatting constructs are not fully evaluated. Resolution is cached only within the worker import and the corpus is not sent to React or committed. The directory selection can contain at most 128 MiB and takes effect on the next save import; without the browser's directory-selection support or game files, import still works without localization.

CK3 character records use `female=yes` for female and omit `female` for male. To avoid assigning sex to malformed/incomplete records, the omitted-field default requires a nonblank first name and a valid or recognized placeholder birth date; unrecognized explicit values remain unknown. `female=no` and explicit booleans are accepted.

## Historical eligibility

`src/dates.ts` validates Gregorian date components and stores a sortable numeric `year * 10000 + month * 100 + day` key, including negative years. `1.1.1`, `0.1.1` and `9999.1.1` are flagged as possible placeholders rather than trusted dates; this is conservative and not an exhaustive synthetic-date detector. Missing, invalid, placeholder and inconsistent source dates remain visible with quality flags. Birth after snapshot, death after snapshot, death before birth, or a death attached to a living record makes the lifetime inconsistent; its date keys are not used in historical filters.

`historicalPredicate` is the shared SQL implementation for inclusive alive-on, alive-during, born-during and died-during filters. It produces true, false or SQL null (unknown), and excludes/counts unknown eligibility separately. Living records are only known alive through a valid snapshot date; deceased records with missing death are not assumed alive. A query ending after the snapshot is unknown for the whole interval, not a forecast. A person is treated as alive on their recorded death day. Status and ruler filters remain **snapshot** attributes even when a historical filter is active. Retention and pruning mean these counts describe represented records only.

`ageAtHistoricalDate` and `ageAtDeath` return completed years only when birth, death where applicable, snapshot and requested date establish a consistent lifetime; otherwise they return null. `historicalAgeExpression` supplies the equivalent SQL expression and the `historical_age` metric reports count, mean and median over known, alive ages. February 29 birthdays use the same month/day comparison as the existing age calculation.

## Cohorts and metrics

`src/analytics.ts` defines typed cohort filters and a grain-aware metric registry with required fields, supported filters, denominators, aggregation, temporal/comparison and missing-data metadata. `analyticalQuerySql` compiles whitelisted requests, and `queryAnalytics` executes them in DuckDB; the worker accepts an `analytics` message containing an `AnalyticalQuery` and returns bounded rows plus metric definitions. No free-form user SQL is accepted. Supported scopes are selected, world and world excluding the selected dynasty. Only selected scope inherits dynasty/house restrictions; all scopes retain status, sex, ruler, historical, trait and relation criteria.

The compiler first filters one row per character, left-joins houses and dynasties by ID, then selects the requested character, house, dynasty, currently-held title, trait, or recorded relationship grain. Optional grouping is by house or dynasty. House/dynasty/title/trait metrics count distinct IDs, so duplicate trait links or multiple members do not inflate entity counts. Character trait and relation filters use `EXISTS`, avoiding multiplication of character ages or counts. Relationship metrics deliberately count recorded rows, including duplicates and derived links. Entity-grain results include only entities linked to the eligible character cohort, not empty houses or unheld titles. Unresolved IDs remain grouped by their stored ID with a null label and cannot be counted as resolved entities. Mixing metrics of different grains is rejected; unknown historical eligibility is excluded. Mean/median ages omit null values and their count is reported alongside them.

For example, `analyticalQuerySql({ grain: 'character', metricIds: ['population', 'historical_age'], filters, scope: 'selected', groupBy: 'house', traitId: '4', historicalAgeDate: '850.1.1' })` returns distinct eligible member counts and known age aggregates per house without multiplying characters by trait links. Replacing the grain/metric with `house`/`houses`, `title`/`titles`, or `trait`/`traits` selects those entity grains from the same cohort. `src/analytics.test.ts` exercises these cases and independent world comparisons against DuckDB, and `src/real-save.test.ts` tests representative joins on the local gamestate.

`queryCohorts` aggregates from the one-row-per-character view in DuckDB. The selected cohort is dynasty plus optional house, status, sex, ruler evidence and historical eligibility. World uses the same non-dynastic filters independently of dynasty/house. World excluding dynasty excludes that dynasty but includes characters whose dynasty is unknown. Population counts distinct parsed IDs; mean and median age use only non-null ages and expose the corresponding sample size and missing count. Living ages use save date, deceased ages use death date; combining them is not an age-at-one-date metric. Positive `landed_data` or current holder evidence is labeled `Ruler`, all other characters are `Unknown`; no confirmed non-rulers are inferred. This definition can include minor title holders and has not been validated as a complete CK3 ruler classification.

The supplied save's current title holders and character `landed_data` provide positive evidence, but the absence of both does not establish that every supported ruler type or modded realm is represented in these paths. No reliable negative-evidence marker was established from the inspected records, so `Non-ruler` is not assigned. In particular, do not interpret an empty `Non-ruler` cohort as proof that no non-rulers exist.

The cohort controls currently apply only to the new overview. Existing generic chart and table controls are separate; a future shared filter implementation must explicitly define how chart drilldowns and benchmark eligibility compose. IDs and identifiers in generic SQL are validated against dataset columns; user values are quoted. Do not expose arbitrary SQL or remote access.
